# UX 표준 계층 — 통합 아키텍처

> 이 문서는 오늘 실제로 발생한 실패(핸들이 있는 재정렬 리스트에 근거 없이
> 롱프레스를 강제한 것)를 반면교사로 삼아, 그 실패를 구조적으로 막기 위해
> 정리한다. 지식을 쌓는 문서가 아니라 **의사결정 절차**를 정의하는 문서다.

---

## 0. 이 문서가 푸는 문제

매트릭스(CONFLICTS.md)는 "브라우저가 실제로 뭘 하는가"를 실측했다.
이 계층은 "사용자가 실제로 뭘 기대하는가"를 같은 규율로 다룬다 — 추측이
아니라 관찰과 인용으로.

그리고 둘을 연결하는 세 번째 문제가 있다: 사용자 기대(이 문서)와 브라우저
동작(매트릭스)이 다를 때 — 예컨대 "iOS 사용자는 롱프레스로 재정렬을
기대하지만, 브라우저는 touch-action만으로는 그 전환을 안 준다" — 이 둘을
잇는 게 실제 구현이다. 이 문서는 그 이음매까지 다룬다.

---

## 0-1. 이 프로젝트가 증명하는 것과 증명하지 않는 것

이 프로젝트의 모든 산출물(CONFLICTS.md, patterns/*.md,
common-pitfalls.md §4.5·§7, `perception-parameters.md`, evals/)을
합쳐도 **다음 네 가지 이상은 증명하지 않는다** — 이 경계선을 넘어선
주장은 이 프로젝트의 어떤 문서에도 근거가 없다:

```
증명함   코드가 물리 법칙(CONFLICTS.md C1~C13)과 일치하는가
증명함   코드가 플랫폼 공식 표준/관행과 일치하는가 (patterns/*.md §4 라벨)
증명함   입력이 의도한 요소에 도달 가능한가 (perception-parameters.md §1,
         elementFromPoint 히트테스트)
증명 안 함   사용자가 실제로 이 UX에 만족하는가
```

`perception-parameters.md`의 3축(입력/출력/속도) 중 "출력"·"속도"도
결국 첫 세 줄("코드가 ~와 일치하는가", "입력이 도달 가능한가")의
연장이지 네 번째 줄을 증명하는 게 아니다 — HCI 연구·접근성 표준으로
대리 측정한 파라미터의 집합이지, 실제 사용자 반응 그 자체가 아니다
(`perception-parameters.md` §0, `common-pitfalls.md` §10에 같은
경계선이 다른 각도로 한 번 더 적혀 있다).

**단, LLM의 확률적 표준 추론 능력을 활용한 '의도 기반 상호작용 계약(Intent-Driven Interaction Contract)'을 통해 지시문의 빈틈을 메운다**:
사용자가 세부 메커니즘을 일일이 지정하지 않더라도, 프롬프트로부터 의도(Intent)와 기능을 리프팅하여 **[3축 상호작용 계약: 수용 입력 vs 차단 간섭(Interference=0), 가시성/레이어 계층, 반응 지연 vs 애니메이션 듀레이션]**을 사전에 수립함으로써 사용자가 기대하는 플랫폼 표준 UX와의 정렬을 구조적으로 보장한다 (`skills/interaction-doctor/references/ux-contract.md` 참조).

**README 작성 시 반드시 참조한다 — 특히 4단계 작업(예:
`evals/README.md`의 "4. 결과 채점") 전에 반드시 이 경계선을
확인한다.** 채점 결과나 검증 결과를 "사용자가 만족했다/편하다"는
식으로 확대해석하지 않기 위한 절차적 장치다 — evals가 재는 것도
결국 이 네 줄 중 처음 셋이지 넷째 줄이 아니다.

## 1. 우선순위 5단계 — 사용자 기대의 근거 서열

핵심 정정: **사용자가 진짜로 표준이라고 느끼는 건 W3C 문서가 아니라 매일
쓰는 OS와 하드웨어로 몸에 익힌 관성이다.** 이걸 최상위로 올린다.

```
1순위   사용자가 메커니즘까지 명시
        예: "500ms 롱프레스로 재정렬 모드 진입해줘"
        → 그대로 구현. 이 계층은 개입하지 않는다.

2순위   사용자가 시각 레퍼런스/디자인만 제공, 메커니즘은 안 줌
        예: Figma 목업, 스크린샷, "이런 느낌으로"
        → 레퍼런스 안의 시각 신호로 컴포넌트를 식별한다 (§3).
          식별되면 3순위로 넘어간다. 신호가 모호하면 4순위로 처리한다.

3순위   OS/하드웨어 관성 — 최우선 표준
        예: iOS 사용자가 매일 손으로 학습한 동작 (Reminders, Mail 스와이프,
            홈 화면 앱 재배치), Android Material 관성, macOS 트랙패드 관성
        → 사용자의 주 플랫폼(요청·타겟 명시로 추정, 불명확하면 웹 범용
          관성 우선)의 실제 OS/1st-party 앱 동작을 근거로 삼는다.
          이건 문서 인용이 아니라 그 OS를 직접 관찰해서 확인한다.

4순위   소프트웨어적 보편 관행 — OS 표준이 없거나 웹 전용인 경우
        예: 브라우저 자체의 관성 (뒤로가기 스와이프, pull-to-refresh),
            주요 웹 제품 다수가 수렴한 패턴 (Notion, Trello, Linear가
            공통으로 쓰는 방식)
        → OS 관성이 명확한 답을 안 줄 때만 여기로 내려온다.
          "표준"이 아니라 "관행"으로 라벨링하고 근거(관찰한 제품 3개 이상)를 남긴다.

5순위   위 넷 모두 불명확하거나 서로 상충
        → 추측하지 않는다. 확신도를 "미확정"으로 표시하고 사용자에게
          확인을 요청하거나, 가장 가까운 관행을 쓰되 대안이 있음을 명시한다.
```

**오늘의 실패는 2순위(핸들 신호)를 무시하고 곧바로 근거 없는 3순위 판단을
지어낸 것이었다.** 핸들이라는 시각 신호 자체가 "즉시 드래그"라는 OS 관성
쪽으로 강하게 기울어 있었는데, 그 신호를 안 쓰고 롱프레스를 즉흥적으로
선택했다.

### 1-6. 플랫폼 분기 허용 조건 — [신설, 이 절 자체가 새로 추가됨]

**이 하위절은 이번에 처음 추가됐다** — recipes.md 레시피 5(스와이프
삭제)가 이 원칙을 인용하며 존재를 전제했는데, 그 시점까지 이 문서엔
없었다. 소급해서 여기 신설한다.

**원칙**: 같은 값이 두 플랫폼에서 서로 다르다는 게 **공식 API
문서로 정확한 수치까지** 확인된 경우([표준] 라벨, 3순위의 "관찰"이
아니라 "인용 가능한 수치")에 한해, `navigator.userAgentData`(우선)
또는 UA 문자열(폴백)로 실제 분기 코드를 작성하는 걸 허용한다. 절충값
(둘 사이 어딘가의 고정값)을 쓰지 않는다.

**이게 CONFLICTS.md의 기존 관행과 다르다는 것도 명시한다**:
CONFLICTS.md C1~C13 어디에도 `navigator.userAgent` 분기가 없다 —
전부 포터블 단일 코드(C1의 더블탭 자체 구현)나 명시적으로 한쪽 값을
선택하는 절충(C3/레시피4의 8px)으로 해결했다. 이 차이는 의도적이다:
C1~C13이 다루는 값 대부분은 **확률적**이거나(C8/C9/C10의 취소율)
**한쪽만 정확한 수치가 있고 반대쪽은 없는**(C3의 iOS 슬롭 미확정)
경우라 분기해도 근거가 양쪽 다 서지 않는다. 반면 스와이프 커밋
거리(swipe-actions.md §1)는 **양쪽 다** 공식 API 문서에 정확한
근거가 있는 드문 경우다(Android `getSwipeThreshold()`=0.5f, iOS
`performsFirstActionWithFullSwipe`=완전 스와이프 시 즉시 실행) —
이런 경우에만 분기를 허용한다.

**적용 범위를 좁게 유지한다**: "느낌상 다를 것 같다"나 확률적 차이
(C8/C9/C10류)는 이 조항의 대상이 아니다 — 여전히 §4 라벨 규율대로
[표준] 수치가 **양쪽 다** 있어야 분기 후보가 된다. 한쪽만 있으면
지금까지처럼 절충하거나 있는 쪽 값을 그대로 쓴다(C3/레시피4 방식
유지).

## 2. 식별 신호 — §1의 2순위를 실행하는 방법

디자인/레퍼런스만 있고 메커니즘이 없을 때, 시각 요소에서 컴포넌트 유형을
역으로 추론하는 규칙. UX_PATTERNS.md의 각 컴포넌트 항목에 이 필드를 반드시
포함한다.

```markdown
## 컴포넌트: 재정렬 가능한 리스트

**식별 신호** (레퍼런스에서 이걸 보면 이 컴포넌트로 판단)

- 항목 오른쪽에 6-dot/hamburger 아이콘 → 핸들 존재 → 3-A
- 아이콘 없이 카드 전체가 하나의 블록 → 핸들 없음 → 3-B
- 항목에 X/휴지통 아이콘, 좌우 여백 → 스와이프 삭제일 가능성,
  다른 항목("스와이프 액션")과 재확인
- 리스트가 가로 스크롤 + 카드가 균일 폭 → 캐러셀일 가능성, 재정렬 아닐 수 있음
```

신호가 두 가지로 겹쳐 읽히면(예: 핸들도 있고 스와이프도 될 것 같은 디자인)
자동으로 §1의 5순위로 떨어진다 — 사용자에게 "핸들로 재정렬만 되나요, 아니면
스와이프로 삭제도 필요한가요?"처럼 구체적으로 되묻는다.

## 3. 오염 방지 — 중첩된 액션의 우선순위 해소

사장님이 반복해서 짚으신 지점. 하나의 요소나 중첩된 레이어에 여러 제스처가
동시에 걸릴 때, 어느 것이 이기는지를 **매번 즉흥적으로 정하지 않고** 선언
기반으로 고정한다. dnd-kit/RNGH가 실제로 쓰는 방식을 그대로 채택한다 —
새로 발명하지 않는다.

```
각 제스처 인식기가 다음을 선언한다:

  activation_distance   몇 px부터 활성화되는가 (매트릭스 실측값 사용,
                         예: Android 8px, iOS는 단일값 아님 — C3 참조)
  activation_delay       몇 ms 눌러야 활성화되는가 (예: 500ms, C6 실측 근거)
  axis                   가로/세로/자유
  relations
    requireFailureOf     다른 인식기가 "탈락"해야만 이게 활성화됨
    blockedBy            다른 인식기가 이기면 이건 자동 취소
    simultaneousWith      동시 활성화 허용 (예: 스크롤 + 롱프레스 타이머는
                         공존 가능하지만 스크롤이 8px 넘으면 타이머 취소)

해소 규칙: 자기 조건을 먼저 만족하고, 자신을 막는 relation이 없는
인식기가 승리한다. 나머지는 pointercancel로 취소된다 (매트릭스가
이미 실측한 그 신호).
```

### 3-1. 이게 왜 "수학적으로 의도를 도출"하는 것과 다른가

명확히 구분해둔다: 이 메커니즘은 **관측값에서 의도를 역산하지 않는다.**
개발자가 미리 "이 컴포넌트에서는 재정렬이 스크롤보다 우선순위가 낮다"고
**선언**하고, 그 선언들끼리 실행 시점에 기계적으로 경합할 뿐이다. 선언
자체는 §1~2의 절차(OS 관성 → 관행 → 확인 요청)로 결정되지, 좌표 데이터에서
통계적으로 유도되지 않는다. 동일한 좌표가 스크롤도 재정렬도 삭제도 될 수
있다는 건 정보이론적으로 확정 불가능한 문제이고, 여기서 벗어날 방법은 없다
— 다만 그 모호함을 개발자의 명시적 선언으로 미리 없애는 것뿐이다.

### 3-2. 매트릭스에 추가할 새 축

지금까지 매트릭스(C1~C13)는 "충돌 하나 대 하나"만 다뤘다. 실제 앱은
3중 이상 중첩된다 (세로 스크롤 페이지 안의 가로 캐러셀 안의 스와이프 삭제
가능한 카드, 그 카드 안에 재정렬 핸들까지). 이건 새로운 카테고리로
분리한다 — 기존 C1~C13과 성격이 다르다 (2자 충돌이 아니라 소유권 그래프).

```
research/nested-interactions/    신규 카테고리
├── methodology.md               "n중 중첩에서 DOM capture/bubble +
│                                 setPointerCapture로 어떻게 소유권을
│                                 위임하는가"를 실기기로 검증
└── case-01-carousel-swipe-card.md   첫 사례. 매트릭스와 동일 규율
                                     (실기기 검증, 표본 수, 재현 가능)
```

이건 매트릭스 확장이지 이 문서(UX 표준)의 일이 아니다 — 물리 계층
질문(브라우저가 뭘 하는가)이지 기대 계층 질문(사용자가 뭘 원하는가)이
아니기 때문이다. §1~2와 §3~3-2는 서로 다른 문서군에 속한다는 걸 명확히
해둔다.

## 4. 확신도 라벨 — 모든 산출물에 강제

UX_PATTERNS.md의 모든 항목, 그리고 스킬이 실제로 내놓는 모든 코드에
다음 넷 중 하나가 반드시 붙는다. 라벨이 없는 산출물은 산출물로 치지 않는다.

```
[표준]     1차 출처 인용 가능 (W3C, HIG, Material 공식 문서)
[관성]     사용자의 타겟 플랫폼 OS/1st-party 앱에서 직접 관찰 확인
[관행]     플랫폼 표준은 불명확하나 다수 주요 제품이 수렴 (3개 이상 근거)
[미확정]   위 셋 다 불명확 또는 상충. 확인 요청 또는 대안 제시로 처리
```

플랫폼 간 라벨이 갈리면(예: 롱프레스 재정렬 — iOS는 [관성], Android는
[관행] 수준으로 약함) 반드시 둘 다 명시하고, 타겟 플랫폼이 불명확하면
더 약한 쪽 라벨을 채택한다 (과신하지 않는 방향으로).

## 5. 자체 점검 — 코드를 내놓기 전 절차

스킬이 실제로 코드를 생성하기 직전에 강제로 거치는 체크리스트. 지식(1~4절)
이 있어도 이 절차 없이는 오늘처럼 무시될 수 있다.

```
□ 사용자가 메커니즘을 명시했는가? → 예: 그대로 구현, 이하 생략
□ 레퍼런스/디자인이 있는가? → §2 식별 신호로 컴포넌트 판별 시도
□ 판별됐다면 UX_PATTERNS.md에 해당 항목이 있는가?
   있으면 → 그 항목의 라벨(§4)을 그대로 코드 주석/응답에 노출
   없으면 → "이 컴포넌트는 아직 조사되지 않았다"고 명시. 추측 금지
□ 여러 제스처가 같은 요소/중첩 구조에 걸리는가?
   → §3 오염 방지 선언(activation_distance/delay, relations)을
     명시적으로 코드에 남긴다 (숨은 암묵 로직 금지)
□ 최종 응답에 [표준]/[관성]/[관행]/[미확정] 라벨이 하나라도 빠졌는가?
   → 빠졌으면 응답을 내보내지 않고 라벨을 채운 뒤 재확인
□ 실행 가능한 코드 블록(§4류)을 작성했는가?
   → 그렇다면 research/ux-standards/common-pitfalls.md의 §4.5
     체크리스트를 통과시키기 전에는 "자체 점검 완료"라고 표시하지
     않는다 — 자세한 내용은 §5.5 참조
```

## 5.5 전체 파이프라인과 "검증"의 두 종류

지금까지 §1~5는 순서를 갖되 마지막 단계(검증)가 명시적으로 분리돼 있지
않았다. 전체 흐름을 하나로 고정한다.

```
명시적 요구 없음
  → §2  시각 요소로 기능을 확정
  → §1  그 기능에 맞는 최우선순위 상호작용 선정
  → §3  선정된 상호작용이 주변/중첩 코드와 오염되는지 점검
  → §3  오염 있으면 선언 기반 우선순위로 정돈
  → §5  자체 점검 (선언과 코드가 논리적으로 일치하는가)
  → ★  검증 (아래로 분리)
  → 제공
```

**검증은 두 종류이고, 반드시 구분해서 밝힌다. 구분 없이 "검증됨"이라고
말하는 것 자체를 금지한다** — 이게 오늘 실패의 마지막 조각이었다. 코드를
정독하고 논리적으로 맞다고 판단한 걸 "확인했다"고 말했지만, 실제로 화면에서
실행해본 적은 없었다.

```
자체 점검 (self-review)
  실행 없이, §1~4의 선언과 산출 코드가 논리적으로 어긋나지 않는지
  재검토. 항상 가능. 하지만 "실제로 그렇게 동작한다"는 증거가 아니다.

런타임 검증 (runtime verification)
  실제로 그 환경에서 코드를 실행하고, 의도한 상호작용이 눈으로 확인되는
  결과를 낳는지 관찰. 실행 가능한 도구(브라우저 제어, 스크린샷, 사용자의
  직접 확인 등)가 있을 때만 가능하다.
```

**자체 점검에는 하위 게이트가 하나 더 있다.** 코드 블록(§4류)을 작성한
직후, `research/ux-standards/common-pitfalls.md`의 §4.5 체크리스트를
통과시키기 전에는 위 정의의 "논리적으로 어긋나지 않는지 재검토"를
완료했다고 볼 수 없다. 이 체크리스트는 외부 근거가 아니라 이 프로젝트
자신이 런타임 검증에서 실제로 재현한 결함(pointerdown 미확인, 멀티
포인터 미처리 등)에서 뽑은 것이다 — §5.5가 구분하는 두 검증 종류 중
어느 쪽도 아니고, 자체 점검 **안에서** 반드시 거치는 별도 단계다.

**도구가 없어서 런타임 검증을 못 했다면, 산출물에 그 사실을 명시한다.**
"자체 점검만 거쳤고 실제 실행 확인은 안 됐다"고 밝히는 것과, 확인한 것처럼
말하는 것 사이의 차이가 오늘 신뢰가 무너진 지점이다. 후자는 절대 하지
않는다 — 확신 없는 상태를 확신 있는 것처럼 포장하는 게, 아예 검증을
생략한 것보다 나쁘다 (§4의 라벨 규율과 같은 원리).

실행 도구가 있는 환경(예: 브라우저 제어가 가능한 에이전트)에서는 런타임
검증을 실제로 수행하고 나서만 "검증됨"이라는 표현을 쓴다. 없는 환경에서는
"자체 점검만 완료, 실행 확인 필요"라고 항상 명시한다.

## 6. 명시적 한계 — 과신하지 않기 위해 남겨둠

- **좌표만으로 의도를 수학적으로 확정할 수 없다** (§3-1). 이 문서의 어떤
  부분도 그걸 시도하지 않는다.
- **자동 검증(B-2)은 아직 없다.** 이 문서는 "무엇을 참조해야 하는지"와
  "참조했는지 스스로 점검하는 절차(§5)"까지만 제공한다. 절차를 실제로
  따랐는지 외부에서 기계적으로 확인하는 건 별도 과제로 남긴다 — 이전에
  다뤘던 정적 분석의 한계(CSS 캐스케이드 문제)가 여기도 그대로 적용되고,
  여기서는 "핸들이 무엇인가" 자체가 시각적 판단이라 더 어렵다.
- **자체 점검과 런타임 검증은 다르다 (§5.5).** 실행 도구가 없는 환경에서
  나온 산출물은 항상 "자체 점검만 완료"로 표시되어야 하고, 이걸 "검증됨"
  으로 표현하면 안 된다. 오늘 실패의 직접 원인이 이 구분을 지키지 않은
  것이었다.
- **커버리지는 유한하지 무한이 아니다.** 상호작용 원형은 30~50개 규모로
  수렴한다고 보되, 처음엔 5~10개만 채운다. 매트릭스와 같은 "완성도보다
  공개" 원칙을 그대로 적용한다.
- **Playwright(브라우저 자동화)는 렌더링 엔진만 제어하고, 모바일 OS나
  네이티브 브라우저 셸이 구현하는 시스템 제스처는 애초에 자동화 대상
  밖이다.** iOS Safari의 엣지 스와이프 뒤로가기(오염 방지 유형 C,
  `research/ux-standards/nested-interactions/side-drawer-back-gesture.md`
  §5)를 Playwright로 재현할 수 있는지 실제로 실험했다 — CDP로 화면
  가장자리에서 시작하는 완전한 터치 스트림을 주입해도, 데스크톱
  트랙패드 스타일 휠 기반 스와이프를 흉내 내도, headless/headed 어느
  쪽에서도, `overscroll-behavior-x` 유무와 무관하게 **어떤 경우에도
  페이지 내비게이션이 발생하지 않았다**(터치는 페이지에 정상 도달함을
  별도로 확인함 — 주입 자체의 실패가 아니라 그 위의 시스템 제스처가
  아예 반응하지 않는다는 뜻). 이건 이 프로젝트가 우연히 놓친 게
  아니라, Playwright가 자동화하는 건 브라우저 엔진 프로세스이지 iOS의
  네이티브 앱 셸(Mobile Safari)이나 그에 준하는 OS 통합 계층이 아니기
  때문에 **구조적으로 검증 불가능한 영역**이라는 걸 실험으로 확인한
  것이다. 이런 종류의 한계는 "안 해봐서 모른다"와 구분해서, "해봤고
  이 도구로는 원천적으로 안 된다는 걸 확인했다"고 명시해야 한다.
- **호스트 에이전트(Claude Code 등) 자체에 내장된 일반적 행동은 이
  프로젝트의 스킬/CLAUDE.md와 무관하게 항상 발동할 수 있고, 이건
  이 프로젝트가 고칠 수 있는 종류의 문제가 아니다.** 실제로 확인한
  사례: `.claude/CLAUDE.md` 없이 `skills/interaction-doctor/`만
  둔 완전히 격리된 환경에서 새 세션을 열어 인터랙션 코드를
  요청했더니, 에이전트가 이 스킬이나 이 프로젝트의 CLAUDE.md를
  근거로 삼은 게 아니라 호스트에 내장된, 이 프로젝트와 무관한
  "run" 계열 스킬을 스스로 호출해서 "UI 기능이니 브라우저에서
  실제로 동작을 확인하겠다"며 Playwright/`chromium-cli`를 찾다가
  turn 제한에 걸려 끝났다. `common-pitfalls.md` §7 작업 도중 실제로
  재현·관찰한 사건이다. SKILL.md나 이 프로젝트의 CLAUDE.md를 아무리
  다듬어도, 호스트 에이전트가 "UI는 실행해서 확인한다"처럼 스스로
  갖고 있는 습관 자체는 이 프로젝트의 통제 범위 밖이다 — 그래서
  이 프로젝트가 할 수 있는 건 "이런 일이 일어날 수 있다"고 명시하는
  것까지이지, 그 행동 자체를 막는 게 아니다.
