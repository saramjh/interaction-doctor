# 파생 제품 계획 — Skill과 Demo Site

> 이 문서는 실행 계획이 아니라 **설계 정리**다. 언제 만들지는 W1 공개 반응을 보고
> 정한다. 지금은 "무엇을 만들지, CONFLICTS.md와 어떤 관계인지"만 확정해둔다.

---

## 0. 핵심 오해 정정

**CONFLICTS.md는 스킬이 아니다.** 지금 시점에 AI는 이 문서로부터 아무것도
지원받지 않는다 — 스킬 자체가 아직 존재하지 않기 때문이다.

CONFLICTS.md의 역할은 하나뿐이다: **근거 원장(source of truth)**. 모든 수치와
주장이 실기기 로그로 검증됐다는 걸 증명하는 문서이고, 대상 독자는 이 프로젝트를
감사하려는 사람(기여자, 회의적인 방문자)이다. AI가 매 요청마다 읽는 용도가
아니다.

실제로 AI를 돕는 문서(스킬)와 사람이 직접 탐색하는 제품(데모 사이트)은
**둘 다 아직 없다.** 이 문서는 그 둘을 설계한다.

---

## 1. 세 층의 관계

```
                    CONFLICTS.md (원장)
                    ├─ 증상 / 원인 / Precedence 표 / 레퍼런스
                    ├─ 대상: 사람, 감사 목적
                    └─ 우선순위: 정확성 > 압축 > 접근성
                           │
              ┌────────────┴────────────┐
              ↓                          ↓
     skills/interaction-doctor/     demo site (interaction-doctor.dev)
     ├─ symptoms.md (증상 매칭)      ├─ 증상 목록 (클릭 가능)
     ├─ conflicts.md (압축 요약)     ├─ 계기판 없는 순수 시연 (GIF/위젯)
     ├─ recipes.md                  ├─ "이게 네 문제야" 자가진단
     ├─ 대상: AI 에이전트            ├─ 처방 + 이 스킬 설치 링크
     └─ 우선순위: 트리거 정확도       └─ 대상: 바이브코더/주니어 (직접 탐색)
        > 압축 > 정확성                우선순위: 3초 이해 > 시각적 대비 > 정확성
```

세 문서는 **내용이 같아야 하고 형식은 완전히 달라야 한다.** CONFLICTS.md의
숫자가 바뀌면 스킬과 사이트도 갱신해야 한다는 뜻 — 이 동기화 문제를 3번에서
다룬다.

## 2. Skill — AI가 실제로 쓰는 형태

### 2.1 지금 스킬에 없는 것 (설계만 있고 콘텐츠는 비어 있음)

Ops 매뉴얼 Part 2.2에 배포 구조는 잡혀 있었지만 실제 파일 내용은 만든 적이
없다.

```
skills/interaction-doctor/
├── SKILL.md              🚧 미작성
└── references/
    ├── symptoms.md       🚧 미작성 — 25개 증상 문장, 이번 실측으로 훨씬 정확하게 쓸 수 있음
    ├── conflicts.md       🚧 미작성 — CONFLICTS.md의 압축판, 링크만 걸고 본문은 3줄
    ├── recipes.md         🚧 미작성
    └── platform.md         🚧 미작성 — 플랫폼 상수 표만
```

### 2.2 CONFLICTS.md → symptoms.md 압축 규칙

CONFLICTS.md의 C10 섹션(약 120줄)을 symptoms.md에서는 이렇게 줄인다.

```markdown
## "드래그하면 화면이 같이 스크롤돼요"

**원인** touch-action 미선언. 브라우저가 스크롤을 컴포지터 스레드에서
즉시 시작함 (JS 리스너 유무와 무관).
**수정** `.item { touch-action: pan-y }` — 세로 스크롤 유지, 가로 드래그 확보.
세로 드래그가 필요하면 CSS만으로는 안 됨 → C6 참조 (롱프레스 전환).
**실측** 3기기 16/16 재현. 상세: CONFLICTS.md#c10
**관련** C6, C9, C12
```

7줄. 원본의 1/15 분량. **원인 한 줄, 수정 한 줄, 나머지는 링크.** 에이전트가
답할 때 이 7줄만 컨텍스트에 얹고, "더 알아야 하면" CONFLICTS.md를 직접 열어
읽게 한다 (Claude Code라면 파일 읽기 도구로 가능).

### 2.3 트리거 설계가 콘텐츠 압축보다 중요하다

스킬의 성패는 `SKILL.md`의 `description` 한 줄이 결정한다. 이건 이미
Ops 매뉴얼 3.3에 초안이 있고, 이번 실측 결과로 증상 문장을 훨씬 정확하게
채울 수 있다. 예를 들어 이전에는 추측으로 썼던 것을,

```yaml
# 이전 초안 (추측)
description: 드래그가 스크롤과 충돌하거나, 모바일에서만 동작이 다르거나...

# 실측 반영 (구체적)
description: >
  터치·포인터 인터랙션이 의도대로 동작하지 않을 때 진단하고 수정한다.
  드래그가 스크롤과 충돌하거나(특히 세로 리스트), 롱프레스가 iOS에서
  전혀 안 먹거나, 핀치 확대가 Android/iOS에서 반대로 작동하거나,
  더블탭이 iOS에서만 씹히는 경우 사용한다. 재정렬 UI(리스트 아이템
  드래그)를 새로 구현할 때도 사용 — 세로 드래그는 CSS만으로 안 풀리고
  롱프레스 전환이 필요하다는 걸 처음부터 알려준다.
```

**증상을 실측된 정확한 언어로 쓸 수 있게 된 게 이번 측정의 실질적 성과다.**
추측이 아니라 "iOS에서만 씹힌다", "Android/iOS가 반대로 작동한다"처럼 구체적
비대칭을 명시하면 트리거 정확도가 올라간다.

### 2.4 세로 재정렬 패턴 — 스킬에 반드시 넣을 것

이번 대화에서 나온 지적("세로 리스트 재정렬은 롱프레스가 표준 UX")이 스킬의
핵심 처방 하나가 된다. C10만 참조하면 이 패턴을 놓친다 — **C10과 C6을 조합한
레시피**가 필요하다.

```markdown
## 레시피: 세로 리스트 세로 재정렬 (dnd-kit 패턴)

CSS만으로 안 풀린다 (C10: pan-y 세로는 16/16 취소, none은 스크롤 사망).
표준 해법은 시간 기반 전환:

1. touch-action: none 은 걸지 않는다 (스크롤을 죽이므로)
2. 500ms 롱프레스로 "재정렬 모드" 진입 (C6: Android contextmenu 494–513ms
   과 맞춰 500ms 사용)
3. 진입 시 해당 항목에 시각 피드백 (들리는 효과 등)
4. 그 이후에만 pointermove로 재배치, 스크롤 억제
5. 참조 구현: dnd-kit KeyboardSensor/PointerSensor 조합
```

이건 CONFLICTS.md에는 아직 없는 내용이다 (C10/C6 각 섹션엔 있지만 조합
레시피로 명시된 적 없음). **symptoms.md를 쓸 때 이 조합 레시피를 최소
3~5개 만들어야 스킬이 실제로 쓸모 있어진다.**

### 2.5 착수 조건

Playbook W2 게이트 그대로: W1 공개 후 반응이 나쁘지 않을 때. 매트릭스
자체가 반응이 없으면 스킬을 만들 이유가 약해진다.

## 3. Demo Site — 사람이 탐색하는 형태

### 3.1 사용자 여정 (사장님이 그리신 그림 그대로)

```
방문 → 증상 목록을 훑는다 (텍스트, 클릭 가능)
     → "이거다" 싶은 항목 클릭
     → Before/After 시연 (계기판 없음, 순수 시각적 대비)
     → 처방 (코드 3~5줄)
     → "이 스킬을 설치하면 에이전트가 자동으로 이렇게 짠다" 안내
```

### 3.2 핵심 제약 — 계기판을 노출하면 안 된다

이번에 GIF 두 번 실패한 이유가 정확히 이 원칙 위반이었다. `tools/*.html`은
**측정 도구**지 **시연 도구**가 아니다. STEP 번호, touch-action 값, pointermove
카운트 같은 걸 보여주는 순간 목표 사용자(바이브코더)는 이해를 포기한다.

데모 사이트의 각 시연 위젯은:

- 판정 텍스트 없음
- 계기판 없음
- 그냥 "고장 난 카드 리스트" vs "정상 카드 리스트" 두 개, 나란히 또는 토글
- 처방은 위젯 **아래**에 별도로, 코드와 함께

### 3.3 콘텐츠는 CONFLICTS.md에서 파생하되 형식은 전혀 다르다

| CONFLICTS.md                     | Demo Site                                    |
| -------------------------------- | -------------------------------------------- |
| "Precedence" 표, 트라이얼 카운트 | "Try it" 인터랙티브 위젯                     |
| "Symptom" 불릿 4개, 서술형       | 목록 페이지의 클릭 가능한 카드 1장           |
| "Resolution" 코드 블록 + 설명    | 코드 블록만, 설명은 위젯이 대신함            |
| 플랫폼별 각주, 🚧 표시           | 생략 (신뢰는 "Verified on" 배지 하나로 대체) |

### 3.4 규모 판단 — 10칸 전부를 위젯화할 필요는 없다

가장 흔한 증상 4~5개만 먼저 위젯화하는 걸 권한다 (C10, C6, C3, C1, C13).
나머지는 텍스트 처방만 두고 위젯은 나중에. Playbook의 "완성도보다 공개"
원칙을 여기도 그대로 적용한다.

### 3.5 스타 자산으로서의 가치

이 사이트 자체가 W1의 "매트릭스 표 직접 삽입"보다 강한 공유 자산이 될
가능성이 있다. Tailwind의 컴포넌트 카탈로그, Can I Use 같은 부류의
북마크되는 참조 사이트 패턴과 같다. **다만 이건 W1 반응을 보고 판단할
문제다 — 지금 만들면 공개가 최소 며칠 밀린다.**

### 3.6 착수 조건

Playbook W1 반응이 좋을 때 (스타 30+ 등 기존 게이트). 반응이 미지근하면
이 규모의 투자는 정당화되지 않는다.

## 4. 동기화 문제 — 세 문서가 어긋나지 않으려면

이번 감사 라운드에서 CONFLICTS.md ↔ DERIVED.md만 두 개인데도 숫자가
어긋나는 사고가 여러 번 났다. 세 번째(스킬), 네 번째(사이트) 문서가 늘면
어긋날 지점이 기하급수적으로 늘어난다.

**원칙**: CONFLICTS.md가 바뀌면 스킬과 사이트는 **그 즉시 갱신 대상 목록에
오른다.** 자동화하지 않는다면(정적 생성 스크립트 등), 최소한 CONFLICTS.md
커밋 메시지에 "affects: skill/symptoms.md#c10, site/conflicts/drag-scroll"
같은 영향 범위를 남기는 규칙을 W2 착수 시점에 정한다.

장기적으로는 symptoms.md/사이트 콘텐츠를 **CONFLICTS.md의 프론트매터에서
스크립트로 생성**하는 게 맞는 방향이다 (예: 각 `### C{n}` 섹션에 YAML
프론트매터로 압축 증상 문구를 미리 박아두고, 빌드 스크립트가 뽑아냄).
지금 단계에서 만들 필요는 없고, 스킬 착수 시점에 재검토한다.
